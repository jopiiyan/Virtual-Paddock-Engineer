# Virtual Paddock Engineer — Project Write-up (for resume / portfolio)

A full explanation of the project with the concrete numbers, written so lines can be lifted
straight into a resume, cover letter, or portfolio page. Numbers are sourced from
[EVALUATION.md](EVALUATION.md); deeper detail lives in [explanation.md](explanation.md).

## One-line summary

Built a full-stack F1 analytics app with a Retrieval-Augmented Generation (RAG) assistant,
plus an evaluation harness that measures whether each "advanced retrieval" technique actually
improves results, and proved with numbers that most do not on this corpus.

## What the project is

Virtual Paddock Engineer is a full-stack Formula 1 analytics application. A React dashboard
compares two drivers' race telemetry (lap pace, tyre degradation, top speed) through
interactive charts, and a RAG chat assistant answers natural-language questions grounded only
in real race data, streaming answers token-by-token over Server-Sent Events and showing the
exact source records behind every answer. The entire application runtime is local: the
generator LLM (`llama3.2`) and embeddings (`nomic-embed-text`, 768-dim) run on Ollama with no
external API keys and zero per-token cost.

The distinctive part is not the app but the **evaluation harness** layered on top. It freezes
a naive dense-retrieval baseline and runs a controlled ablation of three "advanced retrieval"
techniques against it: hybrid search (BM25 + Reciprocal Rank Fusion), multi-query expansion,
and cross-encoder reranking (`BAAI/bge-reranker-base`). Every configuration is scored on
classical IR metrics and on RAGAS answer-quality metrics judged by an independent model
(Google Gemini `gemini-2.5-flash`), deliberately different from the local generator to avoid
self-grading bias.

## What I built (technical scope)

- **Ingestion pipeline** that parses FastF1 telemetry into one natural-language summary per
  driver per stint, embeds each, and stores it in Supabase (PostgreSQL + pgvector, HNSW index)
  with structured `jsonb` metadata for exact filtering.
- **Config-driven retrieval pipeline** (dense leg + BM25 leg + RRF fusion, with optional
  multi-query and cross-encoder reranking) exposed through a single code path, so every
  ablation is one YAML file, not a code fork.
- **FastAPI backend** streaming grounded answers over SSE through a LangChain LCEL chain with a
  strict context-only prompt.
- **Evaluation harness** over a 40-question hand-verified golden set (34 answerable +
  6 unanswerable), producing deterministic IR metrics, RAGAS answer-quality metrics, latency
  profiling, and an abstention-rate check, with every result reproducible from a script and
  appended to an append-only run log.

## Results (the numbers)

- **Corpus:** 2025 British Grand Prix (Silverstone), Race session, 35 chunks, 20 drivers.
- **Golden set:** 40 hand-verified questions across factual, comparative, exact-term, and
  paraphrase types, plus 6 unanswerable.
- **Baseline (naive dense) is the strongest single config:** recall@5 = 0.848, MRR = 0.806,
  nDCG@10 = 0.811. No advanced technique beat it on the top-line ranking metrics.
- **Hybrid search is the one keeper:** best recall@10 (0.971 vs 0.931) and it closed the
  exact-term gap (recall@5 on exact-term went from dense 0.92 to a perfect 1.00), at *lower*
  latency than the baseline (p50 160 ms vs 346 ms) because the in-memory BM25 leg is
  effectively free.
- **Reranking and multi-query did not earn their place:** each rescued one query type while
  regressing others. The full stacked pipeline was both the slowest (p50 ~26 s) and the lowest
  value, and it dropped a factual question the baseline answered perfectly, a concrete case of
  feature-stacking causing harm.
- **Answer quality corroborated retrieval:** an independent Gemini judge (RAGAS) confirmed the
  baseline had the best context precision (0.513) and recall (0.794); no config clearly beat it.
- **Groundedness:** abstention rate = 1.00, the assistant refused all 6 unanswerable questions
  rather than hallucinating.

The honest, deliberately un-triumphant headline: on a small, clean corpus the naive dense
baseline is hard to beat, and the value delivered is the ability to *prove* which components
earn their place rather than stacking features on faith.

## Resume bullets (ready to paste)

- Built a full-stack F1 RAG application (React, FastAPI, LangChain, Supabase/pgvector) with a
  fully local inference runtime (Ollama `llama3.2` + `nomic-embed-text`), streaming grounded
  answers over SSE with per-answer source attribution and zero external API cost.
- Designed a reproducible retrieval-evaluation harness over a 40-question hand-verified golden
  set, ablating hybrid search, multi-query expansion, and cross-encoder reranking against a
  frozen dense baseline on IR metrics (recall@k, MRR, nDCG) and RAGAS answer-quality metrics.
- Proved with data that the naive dense baseline (recall@5 0.848, nDCG@10 0.811) beat every
  advanced technique except hybrid search, which lifted recall@10 to 0.971 at lower latency
  (p50 160 ms vs 346 ms), preventing unnecessary added complexity.
- Used an independent LLM judge (Gemini) separate from the generator to avoid self-grading
  bias, and instrumented latency and a 1.00 abstention rate on unanswerable questions to
  validate groundedness.
